## Q1 · 输入网址后，一定会先做 DNS 吗

> **面试官：** 在地址栏输入一个网址并回车，浏览器第一步做什么？随后一定进行 DNS 查询吗？

**先给结论。** 第一步是把输入文本解析成导航目标，不是立刻 DNS。浏览器先判断它是搜索词还是 URL，补全协议与路径，并应用 HSTS、安全策略等规则；真正发请求前，还可能被 bfcache、Service Worker 或 HTTP 缓存直接回答。

**输入、输出与依赖。** 输入是地址栏文本和浏览器状态，输出是一份规范化后的绝对 URL 与导航上下文。URL 中的 `scheme`、`host`、`port` 决定 origin；`path + query` 进入 HTTP 请求目标；`#fragment` 只留在浏览器，不会发给服务器。

<Flow>
<FlowStep title="① 识别输入">搜索词交给默认搜索引擎；URL 则按状态机解析，不是用字符串随意切割。</FlowStep>
<FlowStep title="② 规范化">补空路径 `/`、处理 Unicode 主机与百分号编码，并按协议使用默认端口。</FlowStep>
<FlowStep title="③ 导航判定">应用 HSTS、安全与扩展策略，处理当前文档离开、前进后退等状态。</FlowStep>
<FlowStep title="④ 尝试捷径">bfcache 可恢复整页；Service Worker 可合成响应；fresh 的强缓存可直接复用。</FlowStep>
<FlowStep title="⑤ 进入网络">没有可用本地结果，或缓存必须重新验证时，才进入 DNS、连接与 HTTP。</FlowStep>
</Flow>

**常见瓶颈不在解析本身。** 真正昂贵的是错误地址导致的二次导航、`http → https → www` 这类长重定向链，以及本可命中却没有命中的缓存。回答时要强调：**「输入网址 → DNS」只是冷启动且未命中任何捷径的分支，不是唯一流程。**

**追问：`no-cache` 是不是完全不缓存？** 不是。`no-cache` 允许存储，但每次使用前必须验证；`no-store` 才是不允许存储。协商缓存命中 `304` 也发生过网络请求，只是没有重新下载正文。

## Q2 · DNS、TCP/QUIC、TLS 分别解决什么问题

> **面试官：** 域名解析之后发生了什么？TCP 三次握手、TLS 握手和 HTTP 请求是什么关系？HTTP/3 改变了什么？

**先给结论。** DNS 解决「去找哪个 IP」，TCP 或 QUIC 解决「建立可传输数据的连接」，TLS 解决「确认对方身份并保护通信内容」，最后 HTTP 才在这条连接上表达「我要哪份资源」。

- **DNS：** 输入主机名，输出 A / AAAA 等记录与 TTL。浏览器、系统、递归解析器任一层的缓存命中，都能省去后续查询。
- **TCP：** 通过 SYN → SYN + ACK → ACK 建立连接，通常花费 1 个 RTT。它提供有序、可靠字节流，但不验证网站身份。
- **TLS：** 校验证书链与主机名、协商密钥，并通过 ALPN 确定应用协议。TLS 1.3 完整握手通常再花 1 个 RTT。
- **QUIC：** 把可靠流、拥塞控制和 TLS 1.3 合并进基于 UDP 的传输协议，首次握手通常 1 RTT；恢复会话可支持 0-RTT，但要处理重放风险。

<Formula expr={`冷启动网络预算（示意） ≈ DNS 1 RTT + TCP 1 RTT + TLS 1.3 1 RTT + 请求/响应 1 RTT`} />
<Caption>这是无缓存、无复用、串行且不计服务端处理时间的示意。DNS 的真实耗时取决于缓存层级与记录链；HTTP/3 把 TCP 与独立 TLS 两段合并为 QUIC 握手；真实页面还会并行、复用或重定向。</Caption>

**常见瓶颈：** 高延迟网络会放大每一次 RTT；DNS 的 CNAME 链会追加查询；TCP 丢包会影响同一条连接上的所有 HTTP/2 流；证书链错误则不是「慢」，而是直接失败。浏览器会维护连接池，**不是每个请求都重新握手**。

**追问：HTTP/2 已经多路复用了，为什么还要 HTTP/3？** HTTP/2 解决的是应用层队头阻塞，但多个流仍共享一条 TCP 连接，一个 TCP 段丢失可能让所有流等待重传。HTTP/3 的 QUIC 流在丢包恢复上彼此独立，不过仍共享网络拥塞，不代表永远更快。

## Q3 · HTTP 请求与响应里，哪些信息会继续影响首屏

> **面试官：** 浏览器发出的导航请求长什么样？200、301、304 分别把流程带到哪里？TTFB 慢就是后端慢吗？

**先给结论。** 请求把方法、路径、Cookie、可接受的编码和缓存验证器交给服务器；响应除了状态码与 HTML 正文，还通过响应头决定缓存、压缩、安全策略和后续资源行为。

```http
GET /interview/browser HTTP/1.1
Host: example.com
Accept: text/html
Accept-Encoding: gzip, br
If-None-Match: "html-v2"
```

<Table>
<table style="table-layout:fixed">
<colgroup><col style="width:18%" /><col style="width:30%" /><col /></colgroup>
<thead><tr><th>结果</th><th>输出</th><th>后续路径与性能含义</th></tr></thead>
<tbody>
<tr><td><code>200</code></td><td>响应头 + 新正文</td><td>进入解压、解码与流式解析；正文大小和服务端等待直接影响首屏。</td></tr>
<tr><td><code>304</code></td><td>验证结果，无正文</td><td>复用本地缓存正文；省去下载，但已经付出一次请求/响应往返。</td></tr>
<tr><td><code>301 / 308</code></td><td>永久跳转地址</td><td>浏览器跟随 Location；新 origin 可能重新 DNS、建连与 TLS。</td></tr>
<tr><td><code>302 / 307</code></td><td>临时跳转地址</td><td>同样增加导航链路；307 保持原方法和正文。</td></tr>
<tr><td>4xx / 5xx</td><td>错误文档或失败</td><td>仍可能有可渲染的错误页；不要把「收到响应」等同于「业务成功」。</td></tr>
</tbody>
</table>
</Table>

**依赖关系要说到响应头之后。** `Content-Encoding` 决定如何解压，`Content-Type` 决定 MIME 与字符集，`Cache-Control / ETag` 决定下次能否复用，`CSP` 等策略会影响资源能否执行或加载。它们都是首屏流程的输入，不是与渲染无关的元数据。

**TTFB 的口径容易答错。** DevTools 的 Waiting (TTFB) 通常从请求发出算到首个响应字节，不包含此前的 DNS、TCP 和 TLS。TTFB 高可能是后端计算，也可能是 CDN 未命中、回源、服务器排队或网络传输；需要结合 `Server-Timing` 与后端 trace 定位。

## Q4 · HTML 还没下载完，CSS、JS 和图片会开始下载吗

> **面试官：** 浏览器什么时候发现子资源？为什么有些图片很晚才出现在 Network 面板？

**先给结论。** 会，而且通常应该尽早并行。HTML 是流式解析的，不必等整份文档下载完成；主解析器构建 DOM 的同时，**预加载扫描器**会向前扫描字节流，提前发现 CSS、JS、部分图片等资源并发起请求。

**输入与输出。** 输入是持续到达的 HTML 字节，以及随后解析出的 CSS；输出是一组带优先级的子资源请求。资源发现的早晚取决于它写在哪里：

<Table>
<table style="table-layout:fixed">
<colgroup><col style="width:19%" /><col style="width:31%" /><col /></colgroup>
<thead><tr><th>资源</th><th>通常如何被发现</th><th>常见瓶颈</th></tr></thead>
<tbody>
<tr><td>CSS</td><td>HTML 中的 <code>link</code> / <code>style</code></td><td><code>@import</code> 串行追加请求；关键 CSS 过大。</td></tr>
<tr><td>JS</td><td>HTML 中的 <code>script</code>、模块依赖图</td><td>同步脚本阻塞解析；动态 import 或客户端路由发现更晚。</td></tr>
<tr><td>图片</td><td><code>img</code>、<code>source</code>、CSS 背景图</td><td>由客户端 JS 插入或藏在大 CSS 中，发现晚；候选尺寸错误会多下载。</td></tr>
<tr><td>字体</td><td>CSS 规则与实际文字需要该字体时</td><td>发现晚、字体文件大、不可见文本期推迟首屏。</td></tr>
</tbody>
</table>
</Table>

**预加载扫描器不是第二个 DOM 构建器。** 它只提前发现资源，不执行脚本，也不能理解所有由 JS 动态生成的依赖。`<link rel="preload">` 可以显式提示「首屏关键但发现较晚」的资源，`preconnect` 则提前为关键第三方完成 DNS、连接与 TLS；两者都不能无差别滥用，否则会抢带宽和连接。

**常见瓶颈的完整表达：** 不只是「网速慢」，还包括**发现晚、优先级低、连接排队、缓存未命中、压缩不足、第三方响应慢**。优化前先确认是哪一段，不要看到资源大就只会开懒加载。

## Q5 · HTML 如何变成 DOM，脚本为什么会卡住解析

> **面试官：** DOM 是怎么构建的？普通 script、defer、async、module 的执行时机有什么区别？

**先给结论。** 响应先按 `Content-Encoding` 解压，再按字符集解码为文本；Tokenizer 将文本切成标签、文本与注释，Tree Construction 按 HTML 规则生成 DOM。解析是流式的，但经典脚本可能让主解析器暂停。

DOM 构建的输出不是「源代码的复制」，而是一棵可被 JS 实时修改的节点树。HTML 解析器会补隐式节点、容错和修复结构，所以「查看源代码」与 DevTools Elements 里的 DOM 不一定相同。

<Table>
<table style="table-layout:fixed">
<colgroup><col style="width:18%" /><col style="width:25%" /><col style="width:29%" /><col /></colgroup>
<thead><tr><th>脚本方式</th><th>下载是否阻塞解析</th><th>执行时机</th><th>面试时要补的限制</th></tr></thead>
<tbody>
<tr><td>经典 <code>script</code></td><td>是</td><td>下载后立即执行，再继续解析</td><td>执行也占主线程；可能读取样式而等待 CSS。</td></tr>
<tr><td><code>defer</code></td><td>否</td><td>解析完成后、DOMContentLoaded 前</td><td>多个 defer 按文档顺序执行。</td></tr>
<tr><td><code>async</code></td><td>否</td><td>下载完成后尽快执行</td><td>不保证顺序，也可能打断解析；适合独立脚本。</td></tr>
<tr><td><code>{'type="module"'}</code></td><td>否</td><td>默认按 defer 语义执行</td><td>还要等模块依赖图就绪；加 async 可改变时机。</td></tr>
</tbody>
</table>
</Table>

**DOMContentLoaded 的边界：** 它在 HTML 解析完成、deferred 脚本与默认 deferred 的模块脚本执行后触发，不等待普通图片全部下载。`async` 脚本不参与阻塞它，可能在事件之后才执行；它也不表示首帧已出现，更不保证 SPA 已完成水合。

**常见瓶颈：** 头部同步脚本会串联「脚本下载 → 执行 → 后续 HTML 解析」；过大的同步 JS 会形成长任务；庞大 DOM 又增加树构建、样式匹配与布局成本。`defer` 只移动执行时机，**不会把执行成本变成零**。

## Q6 · CSS 和 JS 到底谁在阻塞谁

> **面试官：** CSS 会阻塞 DOM 解析吗？什么是关键渲染路径？怎样减少首屏阻塞？

**先给结论。** CSS 通常不直接阻塞 DOM 树构建，但会阻塞首屏渲染；已经解析且仍在加载的样式表，还可能阻塞后续脚本执行。经典脚本则可直接阻塞 HTML 解析，并通过 DOM 未就绪间接拖住首帧。

<Flow>
<FlowStep title="HTML → DOM">提供结构与内容；不必等整个 HTML 下载完。</FlowStep>
<FlowStep title="CSS → CSSOM">解析选择器、层叠、继承与自定义属性，形成样式规则。</FlowStep>
<FlowStep title="Style → Render Tree">DOM 与 CSSOM 汇合，计算每个可见节点的最终样式。</FlowStep>
<FlowStep title="Layout → Paint → Composite">算几何、记录绘制、栅格化并合成，才提交首帧。</FlowStep>
</Flow>

**为什么脚本可能等 CSS？** 脚本可以调用 `getComputedStyle()` 或读取布局信息。如果它依赖的样式表尚未就绪，浏览器就无法给出可靠结果，因此会让相应脚本等待。于是可能出现「HTML 等 JS、JS 等 CSS、CSS 等网络」的串联。

<Callout type="warn">
	<strong>两个常见错误：</strong>「CSS 会阻塞所有 DOM 解析」过于绝对；「defer 脚本不影响首屏」也不成立。脚本即使不阻塞解析，下载、编译与执行仍会消耗带宽和主线程。
</Callout>

**优化要对应依赖：** 精简并拆分关键 CSS，避免用 `@import` 串行加载；有依赖顺序的脚本优先 `defer` 或模块；独立第三方脚本才考虑 `async`；首屏 LCP 图保持 eager，必要时提高优先级；字体用合适的 `font-display` 与后备字体尺寸匹配兼顾可见性和 CLS。

## Q7 · 从 Render Tree 到屏幕，中间经过哪些步骤

> **面试官：** 浏览器渲染流水线是什么？回流、重绘、合成有什么差别？

**先给结论。** 样式计算得到可见节点与计算样式，Layout 计算位置和尺寸，Paint 生成绘制指令，Raster 把绘制变成瓦片位图，Composite 将图层合并并交给 GPU 上屏。

**Render Tree 不是 DOM 的镜像。** `display: none` 不进入渲染树，也不占布局空间；`visibility: hidden` 仍保留几何位置；伪元素会产生参与渲染的盒子。首帧只要求视口内的内容完成必要的样式、布局与绘制，不等整页资源加载完毕；但布局计算仍可能覆盖整个文档。

**常见瓶颈有三类：**

1. **强制同步布局与布局抖动。** 在同一帧里交替读取 `offsetHeight` / `getBoundingClientRect()` 和修改几何样式，浏览器被迫反复布局。
2. **昂贵绘制。** 大面积阴影、滤镜、复杂背景会增加 Paint 与 Raster 成本。
3. **图层失控。** 给大量元素滥用 `will-change` 或 3D transform，会增加显存、栅格化与合成管理成本。

**追问：transform 动画一定不触发布局和绘制吗？** 只能说通常可以走合成路径。元素是否升层、文字是否重新栅格化、滤镜与其他属性是否同时变化，都会影响真实流水线；要用 Performance 与 Layers 验证，不能把经验规则当保证。

## Q8 · 什么时候才算「首屏加载完成」

> **面试官：** 首屏时间用什么指标衡量？DOMContentLoaded 或 load 能代表加载完成吗？

**先给结论。** 「首屏加载完成」不是浏览器唯一标准事件，必须先定义产品目标：第一次出现内容看 FCP，主要内容出现看 LCP，布局稳定看 CLS，操作响应看 INP。DOMContentLoaded 和 load 是生命周期事件，都不能单独代表用户已经完成阅读或交互。

**30 秒版本的口头回答：**

> 浏览器先把输入解析成绝对 URL，并检查 bfcache、Service Worker、HTTP 缓存与重定向；需要联网时，再通过 DNS 得到 IP，建立并复用 TCP 或 QUIC 连接，HTTPS 下完成 TLS，然后发送 HTTP 请求。响应字节到达后解压、解码并流式解析 HTML，同时预加载扫描器并行发现 CSS、JS、图片等资源。DOM 与 CSSOM 汇合形成渲染树，经布局、绘制、栅格化和合成提交首帧。这里 CSS 主要阻塞渲染，经典脚本阻塞解析，defer 和 async 改变脚本时机。最后要区分 FCP、LCP、DOMContentLoaded、load 与可交互，用 LCP、CLS、INP 和真实用户数据判断首屏体验，而不是说所有资源下载完才算结束。

## 面试官可能继续追问

<Disclosure title="为什么说「三次握手之后还要 TLS」只在部分协议路径成立？">
	HTTP/1.1 与 HTTP/2 通常跑在 TCP + TLS 上，因此可以先描述 TCP 三次握手，再描述 TLS 握手。HTTP/3 使用 QUIC，TLS 1.3 已合并进 QUIC 握手，不能再机械地画成「TCP → TLS → HTTP/3」。回答前先声明协议路径。
</Disclosure>

<Disclosure title="强缓存、协商缓存与 Service Worker 谁先生效？">
	已注册且控制当前页面的 Service Worker 能在 fetch 事件中决定返回缓存、网络响应或合成响应，因此它会改变普通 HTTP 缓存路径；没有 SW 接管时，再按 HTTP 缓存新鲜度决定直接复用还是条件验证。前进后退还可能更早命中 bfcache，整页恢复而不重新走资源加载。面试中先说明导航类型与 SW 是否控制页面，比背固定顺序更准确。
</Disclosure>

<Disclosure title="preload 和 preconnect 能随便多加吗？">
	不能。preload 提高指定资源的发现与加载优先级，preconnect 为某个 origin 提前完成 DNS、连接与 TLS；两者都会消耗带宽、连接与 CPU。只对首屏关键且确实会被使用的资源做提示，并验证它没有被重复下载或挤占更重要的 LCP 资源。
</Disclosure>

<Disclosure title="为什么首屏主图不应该 loading=lazy？">
	懒加载的目的是推迟首屏之外、滚动后才需要的图片。若把视口内最大的主图也 lazy，浏览器会推迟它的请求与绘制，通常直接拖慢 LCP。首屏主图应 eager，写准宽高或宽高比，并通过 srcset / sizes 选择合适资源；是否 preload 还要看它原本的发现时机。
</Disclosure>

<Disclosure title="Network 面板里应该按什么顺序排查？">
	先看主文档是否重定向、缓存命中以及 DNS / Initial connection / SSL / Waiting / Content Download 各段耗时，再看关键请求链和资源优先级。若 Waiting 高，继续查 CDN 与后端；若资源早已下载但首帧仍晚，就转到 Performance 查脚本长任务、样式、布局与绘制，不要一直只在 Network 里找答案。
</Disclosure>

<Disclosure title="怎样把这道开放题答得比「背流程」更好？">
	主动补三个边界：第一，缓存、连接复用和 HTTP/3 会改变路径；第二，下载、解析、渲染存在并行与阻塞依赖，不是严格串行；第三，首屏完成要先定义指标。最后用一次真实排查作收尾，例如「我先看主文档 TTFB，再看关键请求链，最后用 Performance 确认是否是主线程长任务」。
</Disclosure>
