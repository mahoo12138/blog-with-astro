## 起点：同一个 User，写了两遍

先说一件小事。

做全栈或后端开发的人，大概率都踩过时间类型的坑：后端在 Go 里用 `time.Time` 结构体序列化，前端拿到的是一个 ISO 字符串。某次联调，页面上的创建时间整整差了八个小时。我从浏览器的 Network 面板一路翻到后端数据库日志，最后发现是前端把带时区的时间字符串当成本地时间给解析了一遍。

修完那个 Bug，我面无表情地在前端和后端的工程里，各自写了一遍 `User` 的定义：

```typescript
interface User {
  id: string;
  name: string;
  createdAt: string; // 后端是 time.Time，序列化之后到底是什么格式？谁说了算
}
```

```go
type User struct {
	ID        string    `json:"id"`
	Name      string    `json:"name"`
	CreatedAt time.Time `json:"createdAt"`
}
```

这两段代码摆在一起，看起来很像，但实际上毫无关系。

明天字段要改名、`name` 从必填变成可选、或者 `createdAt` 从 RFC3339 换成时间戳毫秒数，编译器两边都不会吭一声：TypeScript 只认识前端那份，Go 只认识后端那份。中间那段契约的同步，全靠工程师个人的记性、Code Review 时的肉眼核对，或者等上线之后由用户替你发现。

OpenAPI 代码生成我用过，把契约先写成 Protobuf 再双向生成也用过。这类工具确实省掉了手抄的体力劳动，但省不掉“两份代码”这件事：生成器吐出来的依然是两份隔离的源码，谁先改、谁后生成、生成的文件要不要提交进 Git，全是流程层面的妥协。工具可以把重复搬砖挪个地方，却搬不走“**同一个业务事实被表达了两次**”这个本质问题。

更让我耿耿于怀的，是关于这两种语言特质的一点反差。

TypeScript 的类型系统其实相当能打：结构类型、字面量类型、联合类型、条件类型、模板字面量类型……它的静态表达力比绝大多数工业级语言都要灵活细腻。可问题在于，**它只在编辑器和编译期活着**。`tsc` 跑完之后，所有的类型注解像尘土一样被全部抹除，运行时一个字节都不剩，本质上还是在跑无类型的 JavaScript。

而 Go 的类型系统虽然偏向朴素，但每一个类型都是实打实要落到内存布局、调用约定、虚表和对齐规则上的——**它是能实打实换来机器码的东西**。

一边是有极其强大的类型表达力却在运行时没有实体，另一边是有坚实的物理实体却表达繁琐。我想要的其实是两者交汇的地方：**同一份类型契约，既能用 TypeScript 那样顺滑的语法去书写，又能真的参与编译，最后变成一段脱离任何 JS 虚拟机、能独立运行的原生代码。**

## 一个想法：语法借 TypeScript，后端借 Go

顺着这个念头往下想，最核心的问题立刻浮出水面：“编译器后端怎么办？”

自己手写代码生成？寄存器分配、调用约定（ABI）、栈增长检测、垃圾回收（GC）写屏障……每一样都能单独耗掉几个月甚至几年时间，而且我大概率最终只会写出一个“在演示环境能跑、稍微跑点复杂逻辑就随缘崩溃”的玩具。

上 LLVM 呢？那得先把高级类型系统降到 LLVM IR，再自己从零接一套内存分配器和 GC 运行时，复杂度和工作量只是换了个地方堆砌而已。

想了一圈，**Go 在这里几乎是现成的最优解**。

Go 的标准编译器前端和后端是高度解耦的，它已经把目标文件生成、指令选择、SSA 优化、寄存器分配、平台链接、栈增长和并发垃圾回收全做完了。我要做的事情，本质上只是“**把符合它语义的 AST 节点塞进它的编译器流水线里**”。

再加上 Go 编译器编译速度极快、产物是纯粹自包含的静态可执行文件、交叉编译只需指定环境变量——这完美符合我的理想形态：不需要预装 Node、Deno 或 Bun，也不需要携带任何 V8/JSC 引擎，编译完丢到服务器上就能直接跑。

所以，这个项目的轮廓就此定型：**写 TypeScript 的语法，编译出原生二进制，运行时借用 Go 的底层支持。项目名字叫 Tynel。**

在正式动笔之前，必须非常坦诚地说清楚它**不是**什么，免得产生不切实际的期待：
- 它**不打算替代** Node、Deno 或 Bun；
- 它**不打算支持**全量 TypeScript 语法和庞杂的 npm 生态；
- 它**不是**冲着工业级生产编译器去的。

它是一个纯粹的学习型、探索型项目。目标只有一条：**把从 TypeScript 语法到原生二进制这条路完完整整地走通一次，且链路上的每一步都必须可解释、可复现、可被反汇编核对。**

> [!NOTE] 为什么不走 cgo 或 TinyGo？
> 熟悉 Go 生态的读者大概会立刻联想到这两条路。
> 不走 cgo，是因为我不想引入笨重的 C 工具链和复杂的 FFI 跨边界调用开销；
> 不走 TinyGo，是因为它有一套自己裁剪过的轻量运行时，而我看中的恰恰是标准 Go 运行时那套久经工业检验的高性能 GC 和调度器。代价是最终产物带着完整的 Go runtime，体积在 2.4 MB 上下——对于不需要安装任何环境即可裸跑的原生程序来说，这笔账我认为非常划算。

## 战术倒置：为什么第一阶段刻意不碰 TypeScript？

想法很美好，但真正动手时，现实会给你当头一棒：从零写编译器，最常见的阵亡方式是什么？

通常是脑子一热，直接打开编辑器开始写词法分析（Lexer）和语法分析（Parser）。写着写着，铺开了十几个模块：AST 节点定义了一半，符号表写了一半，类型检查器刚起步，代码生成还没影……某天突然发现各个模块根本拼不到一起，热情耗尽，项目成为 GitHub 上又一个烂尾的仓库。

一个人闷头做编译器，最关键的是**建立确定感**：怎么向自己证明这一步真的成了？

在动手写任何代码前，我梳理出了三条事后看拯救了整个项目的原则：
1. **一次只增加一种能力**。每个阶段结束，必须有一个外部可观察、可执行、可核对的物理结果，绝不用“内部架构更优雅了”这种话来自我安慰。
2. **先固定后端，再接前端**。第一阶段坚决不碰 TypeScript 源码。
3. **每个阶段打一个 Git 标签**。标签指向的提交能够独立复现，历史不可篡改，出了问题随时有干净的基准可以回退。

六个阶段的推进路线如下：

| 阶段 | 核心主题 | 这一阶段必须交出的可观察结果 |
| :--- | :--- | :--- |
| **01** | **一份加法描述怎样成为二进制** | 手写中间表示 → 原生程序输出 `42`，改动输入得到 `43` |
| **02** | **从真实 TypeScript 生成二进制** | `tynel build add.ts` 接入真实编译器，完成检查、降级与链接 |
| **03** | **编译条件选择而不多执行一步** | 支持布尔、严格比较、分支、短路求值与三元式 |
| **04** | **编译会更新状态的程序** | 支持局部 `let` 赋值、`while` 循环、递归调用 |
| **05** | **从多个源文件构建一个程序** | 模块解析、跨文件符号身份、`import type` 擦除、初始化拓扑序 |
| **06** | **把原型交付为可使用的编译器** | 稳定命令行、诊断格式、确定性缓存与产物脱机分发 |

这 6 个阶段进一步拆解成了 48 个具体的开发子节点。每个子节点都有极度严苛的正向和负向验收：正向是“能编译加法”，负向是“调用一个不存在的函数必须在编译前被直接拒绝”。写计划时可能会觉得负向验收有点啰嗦，真做起来才发现它才是玩具脚本与严肃编译器的分水岭。

为什么第一阶段要“反直觉”地坚决不碰 TypeScript？

直觉上，写编译器当然应该从“读源码”开始。但如果第一步就去读 TypeScript，你一上来就得同时面对三个巨大的未知数：
1. 前端的词法与语法分析对不对？
2. 中间表示的设计够不够用？
3. Go 底层的内存注入与代码生成通不通？

任何一处出错，你都在三团迷雾里盲人摸象，根本分不清是前端漏了解析、中间丢了字段、还是后端内存节点造错了。

**把战术倒过来：先固定后端**。我们先定义一套最简的中间表示（NIR），第一阶段先用手工写出来的 JSON 作为输入，集中全部精力打通 Go 编译器的内存注入、目标代码生成和链接。

只要后端能稳定交出正确的机器码，后端就成了一块稳固的磐石。到了第二阶段，前端的任务就变得极其纯粹且单一——只要能把真实源码翻译成同一份 NIR 结构，整条链路立刻就能通，根本不会引发后端的连锁反应。

## 第一阶段的实验：先让后端交出 42

于是，第一阶段的输入不是 `.ts` 文件，而是一份纯手工编写的 JSON 文件 `examples/ir/add.nir.json`，用来描述 `add(40, 2)` 这个计算过程：

```json
{
  "schemaVersion": 1,
  "entry": "main",
  "functions": [
    {
      "name": "add",
      "params": [
        { "name": "a", "type": "number" },
        { "name": "b", "type": "number" }
      ],
      "result": "number",
      "body": [
        {
          "op": "return",
          "value": {
            "op": "binary",
            "operator": "+",
            "left": { "op": "param", "name": "a" },
            "right": { "op": "param", "name": "b" }
          }
        }
      ]
    },
    {
      "name": "main",
      "params": [],
      "result": "void",
      "body": [
        {
          "op": "print",
          "value": {
            "op": "call",
            "function": "add",
            "args": [
              { "op": "number", "bits": "0x4044000000000000" },
              { "op": "number", "bits": "0x4000000000000000" }
            ]
          }
        }
      ]
    }
  ]
}
```

跑起来的命令非常简洁（首次运行需要准备好一份隔离的专用 Go 工具链）：

```zsh
# 构建修改版编译器和开发入口工具
./bridge/go/build
./tools/build

# 把手写的 NIR 描述编译成原生可执行程序，输出到 out/add
./bin/tynel build-ir examples/ir/add.nir.json -o out/add

# 运行刚生成的程序
./out/add
```

终端里的输出只有一行：

```text
$ ./out/add
42
```

第一次在终端里看到这个 `42`，我盯着屏幕愣了好一会儿。

它实在太朴素了——没有 Node 启动时的延迟，没有 V8 的横幅，按下回车瞬间打印出数字，然后进程干脆利落地退出。产物大约 2.4 MB，不依赖 TypeScript 源码，不依赖 Node 环境，甚至不需要我们刚刚构建的编译器本身就能脱机独立运行。

但光看到 `42` 还不能高兴太早：万一编译器在编译期偷懒，直接做常量折叠把 `42` 硬编码写进数据段了呢？

所以，真正让我心跳加速的不是 `42`，而是把输入里的 `40` 改成 `41` 之后，输出跟着变成了 `43`：

```zsh
# 复制一份描述，把第一个实参从 40 改成 41
cp examples/ir/add.nir.json out/add-41.nir.json
perl -pi -e 's/0x4044000000000000/0x4044800000000000/' out/add-41.nir.json

# 重新编译并执行，预期输出 43
./bin/tynel build-ir out/add-41.nir.json -o out/add-41
./out/add-41
```

```text
$ ./out/add-41
43
```

> [!TIP] 踩坑记趣
> 这条修改命令最初我顺手写的是 macOS 风格的 `sed -i ''`，但在跨平台和特定 shell 下容易报语法错，后来统一换成了行为更确定、跨环境一致的 `perl -pi -e`。技术文档里的每一条可执行命令，都经受过反复的手工核验。

在生成二进制的同时，`build-ir` 会打印本次构建的身份哈希，并在产物旁边留下元数据记账文件：

```text
已生成 out/add（2429842 字节）
  输入     c9f89f9d0444
  编译器   6907329847eb
  构建记录 out/add.build.json
```

这两个哈希是整套构建体系的核心底气：它们将“**输入的内容**”与“**当时编译器的确切版本**”唯一绑定。

实验骨架彻底立住了。但“程序输出了 42”离真正理解它还差得很远。接下来，我们要回答贯穿第一阶段的四个核心技术问题：
1. 这份 JSON 中间表示究竟表达了什么？
2. 为什么数字必须存成十六进制位模式？
3. 工具链是如何在不侵入 Go 安装目录的前提下截获编译流程的？
4. 为什么坚决不走“生成 `.go` 源码再编译”的常规路线？

## 中间表示（NIR）：把两种知识彻底解耦

先看这份 JSON 描述的内容。它里面没有 TypeScript 的语法糖，也没有 Go 的具体语法，只承载最纯粹的计算图结构：

| 语义层级 | 在 NIR 文件中的具体表现 |
| :--- | :--- |
| **模块** | 协议版本 `schemaVersion`、入口函数名 `entry`、函数定义列表 |
| **函数** | 函数名称、参数列表、返回值类型（当前支持 `number` 或 `void`）、语句序列 |
| **参数** | 参数名称与声明类型（首阶段仅限 `number`） |
| **语句** | 返回语句 `return` 与控制台打印 `print` |
| **表达式** | 数值字面量、参数引用、直接函数调用、二元算术运算 |

这份结构在项目里被称为 **NIR（Native Intermediate Representation）**。

名字只是个代号，重要的是它解决的架构冲突：前端懂得 TypeScript 的静态类型系统、解构、可选链等语法糖；后端懂得机器指令选择、寄存器分配、调用约定和堆栈布局。如果让前端和后端直接拉手对话，两套完全不同维度的知识体系会纠缠在一起，导致代码极度脆弱。

在两者之间插入一层纯净的 NIR，前端的使命被收敛为“把 TypeScript 源码翻译成 NIR”，后端的使命被收敛为“把 NIR 翻译成目标机器码”。双方各自独立演进，互不干涉。

> [!NOTE] 如何理解 NIR？
> 如果你偏向 Go 背景：可以把它看作 `go/ast` 的精炼裁剪版——它有节点、类型和引用，但不包含任何官方编译器内部的私有状态或内存指针；
> 如果你偏向 TypeScript 背景：可以把它看作“AST 剥离了一切语法外衣后的骨架”——圆括号、分号、关键字拼写、`const` 还是 `let` 的差异全部消失，它只保留“计算到底要做什么”，不保留“源码长什么样”。

在内部内存表示上，NIR 的形状非常接近 C 语言的 Tagged Union：每个节点先看 `op` 操作码，再由 `op` 决定后续哪些字段合法，所有操作共享底层的内存槽位。

由于 JSON 天生缺乏联合类型约束，所有字段在序列化后都被平铺开来。为了防止手写 JSON 时出现不合法的多余字段，反序列化器会执行极度严格的白名单校验：一旦发现 `{"op": "number", "name": "x"}` 这种既像数字又像参数引用的畸形结构，直接报错拒绝，绝不宽容忽略。

选择 JSON 作为 NIR 的第一版载体，纯粹是因为它人类可读、手写方便、能纳管进版本控制，而且出错时能一眼定位到坏字段。NIR 既是文件格式也是内存数据结构，这一特性保证了第一阶段后端能在没有前端的情况下独立验证闭环。

## 为什么数字必须存成 64 位十六进制位模式？

如果你打开 `examples/ir/add.nir.json`，第一眼看到的不是我们熟悉的数字 `40`，而是一串看似吓人的十六进制字面量：`"bits": "0x4044000000000000"`。

这绝不是为了故弄玄虚。

TypeScript 的 `number`（遵循 JavaScript 规范）在底层严格采用 IEEE-754 binary64 标准（即双精度 64 位浮点数）：1 位符号位、11 位指数位、52 位尾数位。巧合的是，Go 的 `float64` 在硬件层面上完全是同一种格式，这是两门语言在数值层面能够无缝对接的物理基石。

但如果中间表示直接用十进制文本（如 `"40.0"`）来存，就会在几个致命的边缘用例上悄然翻车：

1. **负零（`-0`）与正零（`+0`）**：在十进制文本里它们通常都被写成 `0`。但在 binary64 里，负零的位模式是 `0x8000000000000000`，正零是 `0x0000000000000000`。在浮点除法中，`1 / -0` 会得到 `-Infinity`，而 `1 / +0` 会得到 `+Infinity`。如果用十进制存储，符号位就会被抹平。
2. **非数（NaN）与载荷位**：NaN 在十进制里无法写成常规数值，而且 IEEE-754 允许 NaN 携带诊断载荷位（Payload）。只有保留位模式，才能保证跨阶段传递时不发生位丢失。
3. **正负无穷（`+Inf` / `-Inf`）**：文本解析容易受到各语言标准库 `atof` 实现差异的干扰。
4. **十进制往返精度损失（Round-trip Loss）**：浮点数转换成十进制字符串再解析回来，在某些临界精度下最后一个二进制位（ULP）可能发生抖动。

因此，NIR 规定：所有数字在传递时，一律使用确切的 64 位十六进制位模式。

存位模式还逼着我们解决了一个隐蔽的设计冲突：Go 编译器内部的常量求值包 `go/constant` 无法表达 NaN 和无穷大，并且会在编译期把 `-0` 自动规整为 `+0`。如果我们把所有数字都作为字面量喂给 Go 的常量系统，`-0` 就会被悄悄吃掉。

最终的解决方案是分道扬镳：对于常规有限数值，通过字面量注入；对于负零、NaN 和无穷大这类特殊值，改走由运行时支持包提供的底层转换函数 `math.Float64frombits` 在启动时动态复原。

**绝不让中间工具替你做主观擅断的取舍**，这是写编译器必须谨记的铁律。

## 工具链拼图：-toolexec 到底干了什么？

当我们敲下 `./bin/tynel build-ir ...` 时，到底发生了什么？

整个构建流水线主要由四个角色协同完成：

```text
+----------------------+   协调调度    +----------------------------------+
|      bin/tynel       |  --------->  |             go build             |
|   (CLI 顶层驱动程序)   |              |        (标准 Go 构建协调工头)      |
+----------------------+              +----------------------------------+
                                                        |
                                                        | -toolexec 转发
                                                        v
                                      +----------------------------------+
                                      |        bridge/go/toolexec        |
                                      |        (进程级拦截包装门卫)        |
                                      +----------------------------------+
                                           |                    |
                         如果是 compile 命令 |                    | 其他命令 (如 link/asm)
                                           v                    v
                        +----------------------+    +----------------------+
                        | pkg/tool/.../compile |    |   pkg/tool/.../link  |
                        | (注入 NIR 的修改版编译) |    |  (标准 Go 静态链接器)  |
                        +----------------------+    +----------------------+
```

1. **`bin/tynel`（驱动）**：负责解析命令行入参、对 NIR 文件执行语义合法性校验、将输入内容在 `.work/build/snapshots/` 下固化为带有哈希特征的快照，并组织环境变量。
2. **`go build`（工头）**：我们并没有自己重写依赖分析和参数拼装逻辑，而是委托给官方的 `go build`。它知道怎么寻找标准库、处理包依赖和控制并发。
3. **`bridge/go/toolexec`（门卫拦截器）**：通过 Go 提供的 `-toolexec` 参数，`go build` 在调用底层具体工具（编译器、汇编器、链接器）时，会把命令先传递给我们的包装程序。包装程序检测到被调用的工具是 `compile` 时，就神不知鬼不觉地将其替换为我们特制的修改版编译器；而面对 `link` 和 `asm` 时，则原封不动地放行。
4. **修改版 `compile`（实际工匠）**：读取 NIR 快照，将其转化为 Go 内部 AST 节点并完成机器码生成。

这种架构带来了三个巨大的工程收益：
- **完全无需污染宿主环境**：我们不需要修改宿主机器上已安装的任何系统级 Go SDK，所有定制拦截全在单次构建进程的上下文中生效；
- **全量利用工业级基础设施**：符号链接、DWARF 调试信息生成、平台适配完全交给官方 `link` 处理，我们不需要在低级细节上重新发明轮子；
- **环境隔离性高**：构建产物可审计、可回滚，去掉 `-toolexec` 之后立刻回到官方默认行为。

> [!CAUTION] 缓存陷阱实录
> 开发时我曾踩过一个极阴暗的坑：`-toolexec` 指定的拦截器本身**不参与 Go 构建缓存键的计算**！
> 有一次我修改了 bridge 的核心逻辑并重新编译，再次运行测试用例时，发现输出居然一字未变，报出完全相同的旧错误。排查了很久才意识到：`go build` 发现源码和输入参数没变，直接命中了缓存里的 `.a` 归档文件，压根没有触发新的编译！
> 最终的破局解法是：把 NIR 内容哈希和编译器二进制的 SHA-256 摘要拼接进构建标记（Build Tags，形如 `tynelapp tynel_<nir8>_<compile8>`）。输入变了或者编译器变了，构建标记必然跟着变化，强行打破陈旧缓存。

## 核心桥梁（bridge）：在内存里造节点，拒绝生成 Go 源码

这是第一阶段最核心、也最容易引起误解的技术抉择：**bridge 坚决不生成任何 `.go` 源码文件**。

写代码生成器（Transpiler）把 NIR 转成一段 Go 源码文本，再调用 `go build`，表面上看似乎最简单。但文本方案有致命的结构性缺陷：
- **符号冲突与转义风险**：如果用户代码里的函数名或变量名叫 `func`、`type`、`import` 怎么办？生成器必须小心翼翼地为所有标识符设计一套极其复杂的转义机制；
- **运算优先级歧义**：复杂的表达式嵌套在转成源码字符串时，必须重新计算括号包裹逻辑，否则可能因运算符优先级导致计算偏航；
- **双重解析开销**：把内存数据序列化成文本，再让编译器从文本反序列化回 AST，徒增无谓的编译时损耗。

因此，Tynel 的做法是：**直接在 Go 编译器的内存进程空间中，构建 Go 的高层 IR 语法节点**。

注入的时机位于 Go 编译器前端的 `gc.Main` 函数中。这个插入窗口被前后两个极其苛刻的约束死死夹住：

```text
gc.Main 编译器主流程:
  ...
  解析 Go 源码
  内联展开 (Inlining)
  -----------------------------> 【最佳注入窗口】
  逃逸分析 (Escape Analysis)       逃逸分析需要遍历完整函数集合；
  Walk 变换 (AST 降阶)            在此之前注入，新函数享有完全相同的优化流水线。
  SSA 构造与优化
  机器码生成与导出
  ...
```

- **不能更早**：如果在内联之前注入，编译器会尝试从所谓 `bodyReader` 中读取跨包函数体的序列化信息，由于我们的函数是人工在内存中凭空构建的，缺乏这部分数据，会当场触发编译器的内部断言崩溃；
- **不能更晚**：如果在逃逸分析之后注入，编译器的主编译循环已经走过，新加入的函数将彻底漏掉逃逸分析和 SSA 降阶，根本无法生成机器码。

在注入窗口内，bridge 逐一将 NIR 节点翻译成 Go 编译器内部的标准数据结构：

| NIR 描述节点 | 对应的 Go 内部 IR 节点 | 说明 |
| :--- | :--- | :--- |
| `number` | `ir.NewBasicLit` | 字面量，填充对应的浮点位模式常量 |
| `param` | `*ir.Name` | 绑定到函数签名中声明的形参符号槽位 |
| `binary (+)` | `ir.NewBinaryExpr(..., ir.OADD, ...)` | 对应 Go 的加法操作原语 |
| `call` | `ir.NewCallExpr(..., ir.OCALL, ...)` | 函数调用原语 |
| `return` | `ir.NewReturnStmt(...)` | 返回语句 |
| `print` | 调用内建辅助函数的 `OCALL` 表达式语句 | 调用底层标准输出 |

构造完成后，调用 `typecheck.Stmts` 对生成的节点树执行标准类型检查，最后把函数指针追加到 `typecheck.Target.Funcs` 列表中。

从这一刻起，这些由 TypeScript 语义转化而来的函数，在 Go 编译器眼里就和它自己原生解析出来的 Go 代码没有任何区别：**享用同一套 SSA 优化算法、同一套指令选择器、同一套寄存器分配逻辑**。

这就是选择复用成熟工业级后端的威力：我们只用不到五百行 bridge 代码，就撬动了整套经过二十年打磨的高性能原生代码生成流水线。

## 机器码核对：反汇编里见真章

编译器输出了 `42`，改动输入输出了 `43`。但对于一个以原生为目标的编译器来说，最后的答卷必须在机器码里交出。

我们使用 Go 工具链自带的 `objdump` 工具，过滤并查看目标程序中 `main.add` 函数的真实反汇编代码（以下为 macOS Apple Silicon / AArch64 架构结果）：

```zsh
# 使用隔离工具链下的 objdump，按函数符号名正则过滤
GO=.work/toolchain/go1.27.3-sdk-darwin-arm64/bin/go
"$GO" tool objdump -s '^main\.add$' out/add
```

```text
TEXT main.add(SB) <autogenerated>
  <autogenerated>:1  FADDD F1, F0, F0
  <autogenerated>:1  RET
```

这一屏反汇编，是整个第一阶段最令人心潮澎湃的画面。

分析一下这短短的两行汇编：
- `FADDD`：AArch64 指令集中的 64 位双精度浮点数加法指令（Float Add Doubleword）；
- `F1, F0, F0`：按照 ARM64 的标准调用约定，前两个浮点入参分别通过浮点寄存器 `F0` 和 `F1` 传入，返回值同样存放在 `F0` 中。这条指令的含义正是：`F0 = F0 + F1`；
- `RET`：函数返回，将执行权与 `F0` 中的计算结果交还给调用方。

整个 `add` 函数干净纯粹到了极点：**一条浮点加法指令，一条返回指令**。

如果在编译阶段发生了常量折叠，反汇编里绝不可能出现 `FADDD` 指令，只会退化成一条普通的常量加载指令。这一小段汇编，铁证如山地向我们证明：**加法运算确实是在原生程序的运行时被 CPU 硬件执行的**。

再看一看主调用方 `main.main` 的反汇编片段：

```text
FMOVD 3280(R27), F0     ; 从只读常量段加载 40.0 的 IEEE-754 位模式到 F0
FMOVD 3272(R27), F1     ; 从只读常量段加载 2.0 的 IEEE-754 位模式到 F1
CALL main.add(SB)       ; 直跳执行加法函数，计算结果保留在 F0
CALL main.tynelPrintFloat64(SB) ; 调用支持包完成标准输出打印
```

没有解释器分发循环，没有动态方法查找，也没有 JS 对象的解包开销。所有的函数调用都是直接的物理地址跳转（Direct Call）。

## 严谨的防线：建立清晰的错误分级体系

一个优秀的编译器，不仅要能在合法的输入上交出正确的二进制，更要在遇到畸形输入时优雅、清晰地拒绝，并给出具有指导意义的错误信息。

我们准备了一个故意调用了未定义函数的负向测试描述 `bad-call.nir.json`：

```zsh
# 尝试编译一个调用了缺失函数 "missing" 的非法描述
./bin/tynel build-ir bridge/go/testdata/bad-call.nir.json -o out/bad
```

终端拦截并输出了如下信息：

```text
tynel: 源码错误 (nir.unknown-function): 调用了不存在的函数 "missing"
```

检查进程退出状态码：

```zsh
echo $?
# 输出：1
```

目标产物 `out/bad` 根本没有被生成。

这个拦截发生在编译流程真正启动之前，由 `bin/tynel` 的静态验证器直接切断。

为什么一定要在最前端拦截？如果把坏输入放行到底层，结局通常只有两种：要么修改版 Go 编译器在生成节点时因找不到符号而直接发生内部崩溃（Panic），要么被迫生成一段在运行时打印“未实现”的脏代码。前者把使用者的源码错误混淆成编译器的质量缺陷，后者把本该在编译期捕获的错误拖延到运行时，无论哪一种都会让调试体验迅速恶化。

因此，从第一阶段开始，Tynel 就确立了清晰的进程退出状态码规范：

| 退出码 | 错误大类 | 典型触发场景 | 处置建议 |
| :---: | :--- | :--- | :--- |
| **0** | **成功** | 构建完成，目标二进制成功产出 | 正常执行产物 |
| **1** | **源码错误** | 语法非法、类型不匹配、引用未定义符号 | 修改输入代码的业务逻辑 |
| **2** | **用法错误** | 未知命令行子命令、参数缺失或格式有误 | 查阅 CLI 帮助手册重新输入 |
| **3** | **能力限制** | 语法合法但当前编译器子集尚未实现（如 `while`、取余） | 换用受支持的语法或等待版本迭代 |
| **4** | **环境缺失** | 基础 Go 工具链未准备、输出目录不可写、源文件不存在 | 检查本地工具链安装与权限配置 |
| **5** | **内部故障** | 编译器本身发生 Panic、外部依赖进程非正常崩溃 | 向编译器作者提交 Issue 附带现场还原 |

严谨区分错误退出码的理由极其朴素：**绝对不能让“开发者的环境坏了”看起来像是“使用者的代码写错了”**。

## 第一阶段做到了什么，留下了什么

到这里，第一阶段的所有既定验收目标全部达成。

回过头看，我们在第一阶段真正确立并验证的成果包括：
- 确立了以 IEEE-754 binary64 位模式为核心的 NIR 中间表示契约；
- 跑通了基于 `-toolexec` 的无侵入式 Go 工具链拦截机制；
- 实现了直接在内存中构造 Go 高层 AST 的 bridge 注入方案；
- 原生编译出了 `add(40, 2)` 的独立可执行文件，并通过反汇编实证了硬件浮点加法指令 `FADDD` 的真实执行；
- 建立了基于输入哈希与元数据追踪的防缓存污染机制，规范了六大退出状态码体系。

而同样重要的，是诚实记录这一阶段**尚未解决的局限**：
- **不认识真实 TypeScript 源码**：当前的输入完全是一份人工手捏的 JSON 文件，`tynel build` 还不存在；
- **缺乏基本控制流**：没有分支（`if`）、没有循环（`while`）、没有局部变量赋值；
- **控制台输出协议简陋**：输出格式直接沿用 Go 的默认浮点打印规则，无穷大输出为 `+Inf`，未与 JS 的 `Infinity` 对齐；
- **平台单一**：全部实验基准仅在 `darwin/arm64` 架构上严格闭环。

但这绝不是遗憾。这份清晰的未完成清单，正是下一阶段精确的靶心。
