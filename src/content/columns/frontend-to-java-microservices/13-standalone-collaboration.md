前面的文章更多在讲"有标准答案"的部分：请求链路怎么走、日志在哪里找、配置怎么安全变更。这一篇要讲的是**没有标准答案时怎么办**——故障横跨三个微服务、只在某个特定账号下复现、需求边界模糊不清、修复方案需要等另一个团队排期。

很多人把"独当一面"理解为纯粹的技术深度，但在实际工程中，它更接近一种结构化的工作方式：先把模糊的现象转化为可验证的问题描述，再把问题转化为别人能直接接手推进的任务。技术只是构建证据链的手段之一。

---

## 前端经验的能力迁移

| 前端日常场景 | 后端微服务对应场景 | 相通的底层能力 |
|---|---|---|
| 线上页面白屏，先看 Network 再查前端监控 | 先看网关日志，再查下游 `error.log` | 严格分层定位，不跳步骤 |
| 偶现 Bug 编写最小复现 Demo | 固定账号 / 参数 / 数据量复现接口异常 | 把"偶发"变成"可验证" |
| 提 Issue 附 Repo 链接 + 复现步骤 + 截图 | 报障附时间戳、URL、账号、日志片段、SQL | 让对方不用反复追问就能开工 |
| 前后端联调时对齐接口字段与空值语义 | 对齐 BO/VO 契约、分页规则、权限标识、时间格式 | 先定契约，减少返工 |
| 修改公共组件前全局搜引用 | 修改 `api-module` 的 DTO/VO 前做影响面分析 | 兼容优先，灰度上线 |

## 一、从现象到根因的五层收窄法

复杂问题排查最怕"直接猜"。严格按照五个层级逐层推进，每层只回答一个核心问题：

| 层级 | 核心问题 | 在本示例系统中的典型证据来源 | 何时可以往下一层推进 |
|---|---|---|---|
| 1. 调用方 / 页面 | 请求发出去了吗？参数和身份凭证带对了吗？ | 浏览器 Network 面板、App 日志、curl 命令 | 确认请求确实到达了网关 |
| 2. 网关层 | 路由匹配了吗？被哪个过滤器拦截了？总耗时多少？ | `[PLUS]` 请求日志、401/403/404 状态码、鉴权过滤器日志 | 请求被正确转发到了目标服务 |
| 3. 业务服务层 | 业务逻辑执行到了哪一步？抛出了什么异常？ | `info.log` / `error.log`、`DUBBO - 服务异常` | 定位到了具体方法与异常行 |
| 4. 下游依赖层 | 是 RPC、Redis、MQ 还是外部接口慢或失败？ | `SpendTime`、连接异常、超时日志 | 确认了"是下游慢"还是"本服务自身慢" |
| 5. 数据层 | SQL 对不对？执行计划健康吗？目标数据存在吗？ | p6spy 真实 SQL、`EXPLAIN`、表数据记录 | 得到了可验证的根因结论 |

### 证据链的三条硬标准

1. **可复现**：别人按照你提供的步骤能够再次看到同一现象；
2. **可定位**：包含精确到秒的时间戳、完整 URL 或方法名、账号 / 租户 / 参数；
3. **可证伪**：你的假设能被一条日志或一次对照实验推翻，而不是停留在"我觉得大概是"。

> 在很多生产环境中，默认的文件日志并没有 traceId（第 10 篇已分析），此时需要用**网关开始时间 + 请求 URL + 业务唯一参数**的组合来代替 traceId 进行跨服务串联。

### 可复用的问题拆解模板

```text
【现象】谁、在哪个环境、什么操作、期望结果是什么、实际结果是什么、什么时候开始出现
【范围】单账号 / 单租户 / 单设备 / 单页面？还是全量？换个账号是否复现？
【时间线】首次出现时间；最近一次相关变更（代码 / 配置 / SQL / 数据）
【分层证据】
  调用方：请求 URL、参数、返回码、返回体
  网关：有无请求开始 / 结束日志、耗时、状态码
  服务：异常第一行 + 第一个 Caused by、关键业务日志
  依赖：RPC SpendTime / 异常、Redis / MQ 报错
  数据：p6spy SQL、EXPLAIN、相关表记录
【假设】最可能的 2-3 个原因，按概率排序
【验证】每个假设用哪个实验 / 日志证实或推翻
【结论】根因层级 + 一句话结论 + 修复方案 + 防复发措施
```

这个模板的核心价值在于：**它逼你在写出"结论"之前，先把各层的证据填满**。填不满的那一层，恰好就是你还没有排查到位的地方。

## 二、最小复现：把"偶发"变成"可验证"

### 场景 1：偶发性故障

- 先统计频率与分布：10 次请求中出现几次？集中在某个时间段、某台实例还是某组参数？
- 用循环请求批量制造样本：固定参数连续调用 20-50 次，逐次记录网关耗时和返回码；
- 关注是否与并发、缓存过期、连接池回收、GC 停顿、定时任务执行存在时间上的重叠；
- 偶发问题切忌只抓一次失败日志就下结论，必须**同时保留成功与失败各一次的完整日志做对比分析**。

### 场景 2：仅在某个账号下出现

按"身份链路"逐项控制变量排查：

1. 换一个**同角色**账号 → 排除账号本身的数据或状态异常；
2. 换一个**不同角色**账号 → 排除菜单 / 接口权限配置（`@SaCheckPermission`）；
3. 换一个**不同部门或数据范围**的账号 → 排除数据权限过滤（`@DataScope`，第 9 篇）；
4. 换一个**不同租户**的账号（若环境开启多租户） → 排除 `tenant_id` 上下文影响；
5. 对比两次请求的 Token 解码内容、`clientid` 头、请求头完整差异。

核心原则：**每次只改变一个变量**，才能准确定位到底是哪个因素导致的差异。

### 场景 3：仅在大数据量下出现

- 先缩小查询范围（追加时间条件、指定主键 ID）观察是否恢复正常，再逐步放大找到性能劣化的临界点；
- 构造边界数据集：刚好超过分页阈值、刚好触发 `IN` 子句的参数上限、刚好让优化器放弃索引走全表扫描；
- 用 p6spy 拿到**经插件改写后的真实 SQL**，结合 `EXPLAIN` 分析 `rows`、`type`、`Extra`（参考第 10 篇的五步法）；
- 关键区分："数据总量增大导致扫描行数线性增长"与"数据分布变化导致索引选择性劣化"，后者换一批测试数据可能就无法复现。

### 复现手段速查表

| 复现手段 | 操作方式 | 注意事项 |
|---|---|---|
| 直连下游服务端口 | 绕过网关直接调用 8081/8082 等业务端口 | 服务仍然注册了统一鉴权拦截器，仍需携带登录 Token；`check-same-token` 为 true 时还需 Same-Token 头 |
| 换账号 / 换角色 | 用不同权限等级的测试账号调用同一接口 | 先记录两次请求的返回码与数据范围差异 |
| 缩小 / 放大查询 | 调整时间范围、ID 范围、`pageSize` | 保留原始参数作为对照基线 |
| 查看真实 SQL | p6spy 标准输出 | SQL 已经被多租户 / 数据权限 / 分页插件改写 |
| 查看 RPC 耗时 | `DUBBO - 服务响应 ... SpendTime` | 区分消费方等待耗时与 Provider 实际执行耗时 |
| 配置对照实验 | 只修改一个低风险开关或日志级别 | 严禁在共享环境做高危配置变更（参考第 12 篇） |

复现用例必须写成可交付的标准格式，而不是聊天记录中的碎片信息：

```text
前置条件：测试环境 A、账号 test_user_01（角色：普通操作员）、设备 ID=D-1001
操作步骤：GET /device/list?pageNum=1&pageSize=10&status=ONLINE
期望结果：返回 10 条在线设备记录
实际结果：返回 0 条，HTTP 200，body 中 total=0
辅助证据：网关 10:21:03 耗时 83ms；p6spy SQL 含 tenant_id=NULL；换账号 test_admin 同参数正常
```

## 三、跨服务问题：先判断归属，再带着证据推动

### 故障责任归属速判表

| 证据出现的位置 | 更可能的责任方 | 应当让对方优先检查什么 |
|---|---|---|
| 网关没有请求开始日志 | 调用方 / DNS / Nginx / 网关路由配置 | 请求是否真正到达了网关进程 |
| 网关返回 401/403 | 鉴权体系（认证服务 + 网关 + 用户权限） | Token 有效性、`clientid` 头、白名单、角色权限配置 |
| 网关返回 404 | 路由配置 / 注册中心 | 路由断言规则、目标服务实例是否健康、StripPrefix 截取 |
| 网关返回 502/503 | 下游服务 / 注册中心 | 服务进程是否存活、注册 IP 是否可达 |
| 下游 `error.log` 有异常 | 该微服务自身 | 异常第一行与 `Caused by` 根因链 |
| RPC 服务异常日志 | Provider 端或注册配置不一致 | Provider 是否注册成功、接口全限定名与 group 是否匹配 |
| Provider 侧出现慢 SQL | Provider 所在模块 + DBA | SQL 执行计划、索引状况 |
| 数据本身不正确 | 上游写入方 / 数据修复 | 谁写入的、什么时间写入的、能否从源头重放 |

需要注意一个重要判断原则：**问题在哪一层被发现，不代表修复责任就在那一层。** 典型的例子是网关返回 502——错误是网关报出的，但根因通常是下游服务未注册或实例 IP 不可达。

### 报障信息必须携带"证据包"

不要只发一句"接口 500 了，帮忙看下"。至少包含以下内容：

```text
环境：测试环境 A
时间：2026-11-06 10:21:03（精确到秒）
接口：GET /device/list?pageNum=1&pageSize=10
账号 / 租户 / 角色：test_user_01 / 000000 / 普通操作员
返回：HTTP 500，body 摘要（脱敏后）
复现：稳定复现，3 步以内
证据：网关日志片段、服务 error.log 片段（含第一个 Caused by）、p6spy SQL
已排除：换账号正常 / 直连服务正常 / 测试环境 B 正常
期望对方：确认 X 接口的 Y 行为，或修复 Z 问题
```

这样做的好处是：对方拿到后不需要来回追问补充信息，也不容易把问题再踢回来。**证据越靠近根因，推动成本就越低。**

## 四、需求边界不清：先对齐契约，再写代码

前端开发者最熟悉的"前后端接口对齐"，在后端微服务间的协作中同样适用，而且需要确认的维度更多：

| 对齐维度 | 必须在动手前澄清的问题 |
|---|---|
| 字段定义 | 名称、数据类型、是否必填、默认值、最大长度 |
| 空值语义 | `null` 和空字符串是否等价；前端展示 null 时应如何处理 |
| 分页规则 | 默认页大小、最大页大小限制、是否允许深分页 |
| 排序规则 | 按什么字段、升序还是降序、空值排前还是排后 |
| 权限控制 | 谁能看、谁能改；是否受数据权限和租户隔离约束 |
| 时间格式 | 时区约定、格式（`yyyy-MM-dd` 还是时间戳）、精度 |
| 大整数 | Long 类型 ID 是否超过 JavaScript 安全整数范围（需检查全局序列化配置） |
| 字典映射 | 存编码还是存中文名称；翻译在前端做还是后端做 |
| 导出需求 | 是否需要导出、列顺序、脱敏要求 |
| 兼容性 | 旧版前端 / App / 第三方是否仍在调用；能否加字段而不改语义 |

在需求评审阶段可以直接发给产品经理或上游的标准澄清问题清单：

```text
1. 这个筛选条件是精确匹配还是模糊搜索？大小写敏感吗？
2. 不传这个参数时，语义是"不过滤"还是"查空值记录"？
3. 存量历史数据没有这个字段时，页面显示空白还是"未知"？
4. 这个字段谁有权修改？修改后要不要记录操作日志？
5. 导出报表要不要包含？列名和列顺序是什么？
6. 这个接口除了当前页面，还有谁在调用？App 端和第三方会不会受影响？
```

这些问题如果不在动手前问清楚，最终大概率会以"返工"的形式回来。

## 五、需要别人改接口：兼容方案与推进方式

### 兼容性方案选型

| 方案 | 适用场景 | 风险等级 |
|---|---|---|
| **新增字段**（优先推荐） | 只是多返回一个值 | 最低，现有调用方自动忽略新字段 |
| 新增接口 | 语义变化大、参数差异大 | 中等，需要新路由 / 权限 / 文档 |
| 修改字段语义 | 旧字段含义需要变更 | **高**，所有调用方必须同步适配 |
| 修改返回结构 | 包装层或分页结构需要变化 | **高**，几乎必然破坏现有调用方 |

原则：**能加字段就不改字段，能新开接口就不复用旧接口。** 如果确实需要变更已有字段的语义，应先新增字段并行运行一段时间（双读），确认所有调用方都已迁移到新字段后再下线旧字段。

### 变更请求的标准七要素

```text
1. 背景：哪个需求或故障驱动了本次变更，为什么现在需要修改
2. 现状：当前接口定义、字段、行为描述（附代码位置或文档链接）
3. 期望：改成什么样，字段名 / 类型 / 空值语义 / 示例值
4. 兼容：现有调用方是谁；采用新增字段还是修改语义；是否需要并行过渡期
5. 影响面：涉及哪些服务、前端、App、第三方集成；是否需要改库
6. 验证：自测方案、对方验证方式、灰度发布顺序
7. 时间：期望联调时间、上线窗口、回滚预案
```

跨服务上线的一般顺序：
- Provider 先上线（先具备新能力），Consumer 后上线（再开始使用）；
- 新增字段先发布、后使用；删除字段先停用、后删除；
- 跨服务改动配合灰度：单实例验证 -> 小流量 -> 全量，网关最后（第 12 篇）。

## 六、把排障结论沉淀为团队资产

每次排障结束后，花 10 分钟写一张"问题卡片"，放进团队知识库或运维手册中：

```text
标题：设备列表在 XX 账号下返回空
现象：...
根因：数据权限维度未配置，SQL 被拼接为 WHERE 1=0
证据：p6spy SQL 截图 / 角色配置截图（脱敏）
修复：补充 role_data_scope 配置记录
防复发：新增角色时必须检查数据权限维度配置完整性
可检索关键词：数据权限、空列表、tenant_id、DEVICE_CATEGORY
```

三条沉淀标准：
1. **写关键词**：否则半年后想搜相似问题时完全找不到；
2. **写证据位置**：不要只写结论，要保留能回溯验证的日志、SQL 或配置截图；
3. **写防复发措施**：如果能转化为检查清单项或自动化测试用例就更好。

沉淀的复利效应非常明显：第 10 篇的故障速查表、本篇的拆解模板，都是下一次排障时可以直接使用的"外挂工具"。

## 思考与实践自测

**Q1：网关返回 502，应该直接找网关团队修复吗？**
不一定。502 是网关报出的状态码，但根因常见于下游服务未注册、实例 IP 不可达、端口不通。应先检查注册中心和服务存活状态，再判断实际责任方。

**Q2：偶发问题始终抓不到失败日志怎么办？**
先统计频率和时间分布规律，通过循环请求批量制造失败样本，并同时保留成功样本做对比分析。不要只看一次失败日志就急于下结论。

**Q3："只在某个账号下"出现的问题，应该先查什么？**
按身份链路逐项控制变量排查：同角色账号 -> 不同角色 -> 部门 / 数据范围 -> 租户 -> Token / 请求头差异。每次只改变一个变量。

**Q4：旧接口需要增加一个返回字段，需要走版本化流程吗？**
通常不需要。新增字段是天然向后兼容的变更；需要版本化的是修改字段语义或变更返回结构的破坏性操作。

**Q5：报障信息中为什么要带"已排除项"？**
它证明你已经做了系统性的分层排查，能显著降低对方的复现成本和沟通轮次，也避免问题被来回踢皮球。
