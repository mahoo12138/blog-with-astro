## 先建立地图：一次导航，四个现场

<Intro>
	<strong>先给结论：</strong>从输入 URL 到看到页面，不是一次「请求—响应」，而是两次转换：
	先把名字变成字节（导航与网络），再把字节变成像素（解析与渲染）。前者主要发生在浏览器进程与网络服务，

## 第一站：URL 不是字符串，而是一份结构化指令

浏览器拿到的第一份输入不是 HTML，而是你键入的文本。它必须先回答：这是搜索词还是 URL？协议是什么？主机是谁？要不要补默认端口？

地址栏本身还带着产品行为：Chrome 可能先尝试把它当 URL，失败后再交给搜索引擎；`https://` 可能被自动补全；HSTS 预加载列表会在请求发出前把 `http://` 升级成 `https://`。这些都不是 URL 标准的一部分，但会改变你最终请求的地址。

## 第二站：按下回车，浏览器先做几次「要不要上网」的判断

导航请求并不总是从网络开始。浏览器会依次尝试几条捷径，任何一条命中，都可能让后面的 DNS、TCP、TLS 全部跳过。

<Flow>
<FlowStep title="① 旧文档">当前页可能进入 bfcache，或触发 `pagehide` / `beforeunload`；如果导航被取消，流程在这里结束。</FlowStep>
<FlowStep title="② Service Worker">已注册的 SW 可以在 `fetch` 事件里直接返回缓存、合成响应，甚至完全离线。</FlowStep>
<FlowStep title="③ HTTP 缓存">强缓存 fresh 直接复用；过期则带条件头 revalidate；命中 304 时只更新头。</FlowStep>
<FlowStep title="④ 重定向">301 / 302 / 307 / 308 可能把请求带到另一个 origin，重新走 DNS、连接与 TLS。</FlowStep>
<FlowStep title="⑤ 网络栈">以上都没有直接答案，才交给 DNS、传输层和 HTTP。</FlowStep>
</Flow>

<Callout type="info">
	**bfcache 是「整页暂停」，不是「重新加载」。** 前进 / 后退时，浏览器可能把整个页面（包括 JS 堆）冻结起来，返回时瞬间恢复。`pageshow` 事件的 `event.persisted` 为 `true` 就是这条路径。
</Callout>

<Tabs>
<Tab label="普通导航">
	走完整的缓存查找：Service Worker → HTTP 缓存 → 网络。强缓存 fresh 时，DevTools 可能显示 `from disk cache` 或 `from memory cache`，请求根本没有发出去。
</Tab>
<Tab label="刷新（F5 / ⌘R）">
	主文档通常会带 `Cache-Control: max-age=0` 重新验证；子资源不一定全部重来。memory cache 可能被绕过，但 Service Worker 仍可能拦截。
</Tab>
<Tab label="强制刷新">
	绕过 HTTP 缓存重新下载主文档。它不等于「绕过 Service Worker」——DevTools 里还要选 `Bypass for network` 才会连 SW 一起跳过。
</Tab>
<Tab label="后退 / 前进">
	优先尝试 bfcache；没有可用快照时才重新导航。监听 `pageshow`，不要假设每次返回都会重新执行脚本。
</Tab>
</Tabs>

<Callout type="warn">
	**`beforeunload` 会伤害 bfcache。** 它要求页面在离开前同步询问用户，浏览器很难安全地冻结这样的页面。需要清理时优先用 `pagehide` / `visibilitychange`，不要为了「保存提示」给所有页面加 `beforeunload`。
</Callout>

### 重定向：状态码决定方法和正文怎么处理

| 状态码 | 语义 | 方法和正文 | 常见用途 |
| --- | --- | --- | --- |
| `301` | 永久移动 | 历史上可能把 POST 改成 GET；浏览器行为并不完全一致 | 域名迁移、永久改路径 |
| `302` | 临时移动 | 同上，方法可能被改写 | 登录后跳转、短期活动页 |
| `303` | See Other | 明确要求用 GET 取新资源 | POST 后跳转到结果页 |
| `307` | 临时重定向 | 保持方法和正文 | 需要保留 POST 的临时跳转 |
| `308` | 永久重定向 | 保持方法和正文 | 需要保留 POST 的永久跳转 |

<Callout type="info">
	**跨 origin 重定向会重新计算安全边界。** `Authorization`、Cookie 的作用域、CORS、Referer 策略都可能变化；重定向链越长，首字节越晚。能一次跳到位，就不要三段跳。
</Callout>

<Disclosure title="为什么 DevTools 里有时显示 from memory cache、from disk cache 或 304？">
	`from memory cache` 通常是当前渲染进程里还活着的资源，生命周期短、读取极快；`from disk cache` 是磁盘上的 HTTP 缓存，跨导航或跨进程仍可能复用。
	`304 Not Modified` 则是「缓存已经过期，但服务器确认内容没变」：浏览器发出条件请求，服务器只回头部，不重发正文。三者都叫「缓存」，但走的路径完全不同。
</Disclosure>

## 第四站：TCP 与 QUIC，先修一条能跑字节的路

拿到 IP 之后，浏览器还要建立传输连接。HTTP/1.1 与 HTTP/2 跑在 TCP 上，HTTP/3 跑在 QUIC 上；QUIC 又跑在 UDP 上。名字不同，核心问题相同：双方如何确认彼此可达、如何控制发送速度、丢包之后谁来等谁。

<Tabs>
<Tab label="TCP：三次握手">
<Flow>
<FlowStep title="SYN">客户端选一个初始序列号，告诉服务器「我想连接」。</FlowStep>
<FlowStep title="SYN + ACK">服务器确认，并给出自己的初始序列号。</FlowStep>
<FlowStep title="ACK">客户端确认。此时连接建立，完整一次往返。</FlowStep>
<FlowStep title="请求">HTTP 字节才开始进入连接；TFO 可以提前带数据，但部署有限。</FlowStep>
</Flow>
	TCP 还会做拥塞控制：新连接从小拥塞窗口开始，确认越多窗口越大。页面小的时候感知不明显；大文件或高延迟链路会明显受慢启动影响。
</Tab>
<Tab label="QUIC：1-RTT 或 0-RTT">
<Flow>
<FlowStep title="Initial">客户端在 UDP 上发 Initial，里面已经带 TLS ClientHello 与密钥分享。</FlowStep>
<FlowStep title="Server Initial + Handshake">服务器回证书、密钥材料和自己的 Finished。</FlowStep>
<FlowStep title="1-RTT 数据">客户端完成握手，开始发 HTTP/3 请求。首次连接 1 RTT。</FlowStep>
<FlowStep title="0-RTT（可选）">恢复会话时可以提前发数据，但服务器要接受重放风险。</FlowStep>
</Flow>
	QUIC 的流是独立的：一个流丢包，不会让其他流一起等 TCP 重传。但拥塞控制仍然共享，网络整体拥塞时所有流都会变慢。
</Tab>
</Tabs>

<Callout type="info">
	**不是每个请求都重新握手。** 浏览器会复用连接池：HTTP/1.1 通常按 origin 开若干条 TCP；HTTP/2 通常一条连接跑多个流；HTTP/3 复用 QUIC 连接，还能用连接 ID 迁移网络（例如 Wi-Fi 切蜂窝）。
</Callout>

<Table>
<table>
<thead><tr><th>版本</th><th>传输</th><th>多路复用</th><th>头部压缩</th><th>典型握手</th><th>主要限制</th></tr></thead>
<tbody>
<tr><td><strong>HTTP/1.1</strong></td><td>TCP</td><td>基本没有（pipelining 很少启用）</td><td>无</td><td>TCP 1 RTT + TLS</td><td>队头阻塞；浏览器常见开约 6 条连接绕过。</td></tr>
<tr><td><strong>HTTP/2</strong></td><td>TCP + TLS</td><td>一条连接上的多个流</td><td>HPACK</td><td>TCP 1 RTT + TLS 1.3 1 RTT</td><td>TCP 层丢包会阻塞所有流；server push 已被主流浏览器移除或不再推荐。</td></tr>
<tr><td><strong>HTTP/3</strong></td><td>QUIC（UDP）</td><td>独立流</td><td>QPACK</td><td>QUIC 首次 1 RTT，恢复可 0-RTT</td><td>UDP 可能被网络拦截；CPU 成本、调试工具与生态仍在演进。</td></tr>
</tbody>
</table>
</Table>

<Callout type="warn">
	**HTTP/2 的多路复用解决的是应用层队头阻塞，不是 TCP 队头阻塞。** 一条 TCP 连接上丢了一个包，后面的所有 HTTP/2 流都要等重传。HTTP/3 把「等」限制在单个流，但网络拥塞、服务器排队和应用依赖仍然存在。
</Callout>

<Formula>
	首个字节的握手账（示意）：DNS 1 RTT + TCP 1 RTT + TLS 1.3 1 RTT + 请求 / 响应 1 RTT<br />
	HTTP/3：DNS 1 RTT + QUIC（含 TLS）1 RTT + 请求 / 响应 1 RTT
</Formula>
<Caption>
	这是「冷启动、无缓存、串行」的下界。真实页面会并行预连接、复用连接、命中缓存，也可能被重定向和慢启动拉长。把它当预算表，不要当秒表。
</Caption>

## 第五站：TLS，先确认对面是谁

TCP 只保证「字节按序到达」，不保证「对面是谁」、也不保证「中间没人改」。TLS 在传输之上补上三件事：身份认证、密钥协商、完整性保护。

<Tabs>
<Tab label="TLS 1.3：1 RTT">
<Flow>
<FlowStep title="ClientHello">客户端发送支持的版本、SNI、ALPN、key_share 和随机数。</FlowStep>
<FlowStep title="ServerHello + 证书">服务器选参数、回证书、密钥材料和 Finished。</FlowStep>
<FlowStep title="客户端 Finished">客户端验证证书链，算会话密钥，回 Finished。</FlowStep>
<FlowStep title="应用数据">HTTP 字节进入加密通道；ALPN 决定用 h2 还是 h3。</FlowStep>
</Flow>
</Tab>
<Tab label="TLS 1.2：通常 2 RTT">
	TLS 1.2 的完整握手需要先协商参数、再交换密钥，通常比 1.3 多一个往返；它还支持一些已被 1.3 移除的旧算法。今天的性能讨论默认以 TLS 1.3 为基线。
</Tab>
<Tab label="0-RTT 与会话恢复">
	客户端拿上次的 session ticket / PSK，直接在第一个 flight 里带 early data。省一个 RTT，但 early data 可能被重放；只适合幂等、低风险的请求，服务端要显式接受。
</Tab>
</Tabs>

<Callout type="warn">
	**HTTPS 不隐藏你访问了哪个域名。** DNS 查询、TLS SNI 和服务器 IP 默认都可能被网络观察者看到。ECH（Encrypted Client Hello）能加密 SNI 的一部分，但需要 DNS HTTPS 记录配合，且并非普遍可用；它也不是「匿名上网」。
</Callout>

<Disclosure title="证书链到底在验证什么？">
	浏览器不是「看证书长得像不像」，而是从站点证书出发，沿着签名链一路走到本地信任库里的根证书。中间任何一环过期、域名不匹配、签名不对或链不完整，都会失败。

	证书链之外，浏览器还会检查主机名（SAN）、有效期、用途（EKU）、吊销状态与证书透明度记录。不同平台对 OCSP / CRL 的策略不同，所以「同一张证书在 Chrome 能开、在某个旧设备不能开」并不奇怪。
</Disclosure>

<Callout type="tip">
	想亲眼看握手，用 `curl -v https://example.com` 看 ALPN 与 TLS 版本，或用 `openssl s_client -connect example.com:443 -servername example.com -alpn h2` 看证书链。注意：这些工具的输出是「这一次连接」的快照，CDN 可能给你分配到不同边缘节点。
</Callout>

HSTS 是另一层保护：服务器通过 `Strict-Transport-Security` 告诉浏览器「以后这个域名只用 HTTPS」，浏览器会记住并在请求发出前把 `http://` 改写成 `https://`。HSTS 预加载列表把这一步提前到首次访问之前，但一旦提交，回滚很慢——上线前要确认全站子域都能 HTTPS。

## 第六站：HTTP 请求与响应，语义与缓存

连接和加密都准备好之后，HTTP 才真正开始。导航通常是一条 `GET` 请求；服务器用状态码、响应头和正文回答。

</Caption>

<thead><tr><th>头字段</th><th>方向</th><th>作用</th><th>常见坑</th></tr></thead>

<tr><td><code>Content-Encoding</code></td><td>响应</td><td>正文压缩算法</td><td>它描述内容的压缩编码（content coding），不是字符集；字符集在 <code>Content-Type</code>。</td></tr>
</tbody>
</table>
</Table>

<Tabs>
<Tab label="首次访问">
	没有可用缓存：请求打到服务器，返回 `200` 和完整正文。响应里的 `Cache-Control` / `ETag` 决定「下一次」能不能省。
</Tab>
<Tab label="强缓存命中">
	响应仍是 fresh（例如 `max-age=31536000, immutable`）：浏览器直接用本地副本，不发请求。DevTools 可能显示 `from disk cache`，Network 面板里没有服务器响应。
</Tab>
<Tab label="条件请求">
	缓存已过期：浏览器带 `If-None-Match` / `If-Modified-Since` 去问。服务器确认没变，返回 `304`，没有正文；浏览器复用旧正文，并可能用新响应头更新元数据。
</Tab>
</Tabs>

<Callout type="warn">
	**`no-cache` ≠ `no-store`。** `no-cache` 允许存储，但每次使用前必须向服务器验证；`no-store` 才是不允许写入任何缓存。另一个常见坑是 `304` 不是错误：它是「验证成功，正文没变」。
</Callout>

<Callout type="info">
	**Cookie 是请求重量的一部分。** 同一 origin 的每个请求都会带上匹配的 Cookie；把大段 JSON 塞进 Cookie，会让 HTML、CSS、JS、图片的每个请求都变胖。会话 ID 用 `HttpOnly` + `Secure` + 合适的 `SameSite`，别把敏感数据放在前端可读的 Cookie 里。
</Callout>

<Disclosure title="CORS 会阻止顶级导航吗？">
	不会。CORS 约束的是 `fetch` / `XHR` 以及部分子资源的跨源读取，不是「地址栏导航」。你从 A 站点链接到 B 站，浏览器不会因为 B 站没给 `Access-Control-Allow-Origin` 就拒绝打开。
	真正影响导航的是 CSP、混合内容、HSTS 与下载策略；`X-Frame-Options` / `frame-ancestors` 约束的是嵌入，不是顶级导航。跨源隔离（COOP / COEP）又是另一套机制，别把它们混成「CORS」。
</Disclosure>

<Formula>导航到首字节 ≈ DNS + 连接（TCP / QUIC）+ TLS + 请求发送 + 服务器等待</Formula>
<Caption>
	注意：DevTools 的 Waiting (TTFB) 只从请求发出算起，不含 DNS / 连接 / TLS。所以「导航到首字节慢」不等于「后端慢」；先看时间花在 DNS、连接、TLS 还是等待服务器，再用 <code>Server-Timing</code> 拆边缘与回源。
</Caption>

## 第七站：字节到达渲染进程，页面还没开始画

网络服务把响应交给渲染进程，但「收到字节」和「可以绘制」之间还有一段路：解码、MIME 判定、字符集、CSP、解析器启动，以及预加载扫描器提前发现子资源。

<Flow>
<FlowStep title="解码">按 `Content-Encoding` 解压，再按 `Content-Type` 的 charset 解码成文本。</FlowStep>
<FlowStep title="判定">确认 MIME、`nosniff`、CSP、下载策略；不是 HTML 就不会进入渲染流程。</FlowStep>
<FlowStep title="解析">HTML tokenizer 开始工作，边下边解析，不必等整个文档。</FlowStep>
<FlowStep title="预加载">预加载扫描器并行寻找 CSS、JS、图片、字体，提前发起请求。</FlowStep>
</Flow>

<Table>
<table>
<thead><tr><th>资源</th><th>阻塞解析？</th><th>阻塞渲染？</th><th>浏览器如何发现</th></tr></thead>
<tbody>
<tr><td>HTML</td><td>—（它就是解析器输入）</td><td>是（首帧需要 DOM）</td><td>导航请求</td></tr>
<tr><td>CSS</td><td>不直接阻塞 DOM 构建</td><td>是</td><td>解析到 <code>link</code> / <code>style</code></td></tr>
<tr><td>经典 <code>script</code></td><td>是</td><td>间接（会拖住 DOM）</td><td>解析器或预加载扫描器</td></tr>
<tr><td><code>defer</code> / <code>module</code></td><td>否</td><td>间接（执行会占主线程）</td><td>预加载扫描器</td></tr>
<tr><td><code>async</code></td><td>否</td><td>间接（执行会占主线程）</td><td>预加载扫描器</td></tr>
<tr><td>图片 / 字体</td><td>否</td><td>通常否；字体会影响文字可见</td><td>解析器、预加载扫描器、CSS</td></tr>
</tbody>
</table>
</Table>

<Callout type="warn">
	**两句话都要修正：**「HTML 下载完才开始渲染」是错的，解析是流式的；「CSS 阻塞 DOM 构建」也不准确，CSS 不直接阻止 DOM 树构建，但会阻塞渲染，并且会阻塞脚本执行。真正让首屏卡住的，通常是「渲染阻塞的 CSS + 阻塞解析的脚本 + 字体」这一组。
</Callout>

<Callout type="tip">
	**预加载扫描器是投机，不是解析器。** 它只根据字节流提前发现资源，不能替代 DOM 构建，也不会执行脚本。`<link rel="preload">` 是给它的强提示，但预加载太多会抢带宽；只对「首屏关键、发现得晚」的资源用。
</Callout>

<Disclosure title="为什么 CSS 会阻塞脚本？">
	脚本可能读取 `getComputedStyle`、`offsetWidth` 等布局信息；如果样式表还没到，浏览器无法给出可靠的计算值。因此，脚本执行前会等待尚未加载的样式表。一个「脚本在 head、样式表在脚本后面」的页面，可能出现脚本等 CSS、CSS 等网络、HTML 又等脚本的串联。
</Disclosure>

<Caption>
	HTML 解析器允许省略结束标签，会补出 <code>tbody</code> 之类的隐式节点，并有一套错误恢复规则。你写的 HTML 不是浏览器最终看到的树；DevTools 的 Elements 面板才是。

<Tabs>
<Tab label="经典 script">
	解析器遇到 `<script src>` 会暂停，下载并执行完才继续。脚本能阻塞后面的 HTML，也会拖住首屏。把脚本放在 `<head>` 又没有 `defer` / `async`，通常是最贵的写法。
</Tab>
<Tab label="defer">
	下载与解析并行，执行推迟到解析完成之后、`DOMContentLoaded` 之前，并按文档顺序执行。依赖顺序的脚本优先用它。
</Tab>
<Tab label="async">
	下载与解析并行，下载完就执行，不保证顺序，也不保证在 `DOMContentLoaded` 前。适合独立的统计、广告、客服脚本；有依赖关系时不要只靠它。
</Tab>
<Tab label="type=module">
	模块默认就是 deferred 的，并且按依赖图执行。`async` 仍然可以让它提前执行，但模块之间的依赖顺序由 import 图保证，不由 `<script>` 顺序保证。
</Tab>
</Tabs>

<Callout type="warn">
	**`DOMContentLoaded` 不是「页面加载完成」。** 它在 HTML 解析完成、deferred 脚本执行后触发；`load` 还要等图片、样式、iframe 等资源。两个事件都不等于「用户已经可以交互」——事件处理器可能还没绑定，水合可能还没完成。
</Callout>

<Disclosure title="DOM 是活的，HTML 不是">
	`document` 是实时树：你改一个节点，`querySelector` 立刻能看到。`innerHTML` 会把字符串重新解析成节点，可能丢失事件监听与状态；`<template>` 的内容是惰性的，不会进入主文档；Shadow DOM 是另一棵树，`document.querySelector` 默认看不到它的内部。
	调试时不要拿「查看源代码」当 DOM：源代码是服务器发来的文本，Elements 面板是解析、脚本修改之后的树。
</Disclosure>

<Callout type="warn">
	**`will-change` 不是银弹。** 它提示浏览器提前升层，但每个层都要显存和栅格化成本；给大量元素或长期保留 `will-change`，可能让滚动更卡。动画结束后移除它，或用 `contain` 限定影响范围。
</Callout>

<Disclosure title="为什么「重绘」和「回流」不是一回事？">
	回流（layout / reflow）重新计算几何：位置、尺寸、换行、滚动范围。重绘（repaint）只重新记录像素：颜色、阴影、背景。改 `width` 往往同时触发布局和绘制；改 `color` 通常只重绘；改 `transform` / `opacity` 往往只走合成。
	但「只走合成」也有成本：图层太多会吃内存，文字在独立层上可能被重新栅格化。优化要看整条流水线，不要只盯一个属性。
</Disclosure>

## 第十一站：第一帧之后，页面才逐渐「活」起来

FCP 只是「有内容画出来了」，LCP 是「最大的内容画出来了」，INP 是「交互响应有多快」，CLS 是「布局有没有跳」。它们测量的是不同阶段，不能用同一个开关解决。

<Table>
<table>
<thead><tr><th>指标</th><th>测量什么</th><th>常见瓶颈</th><th>先看哪里</th></tr></thead>
<tbody>
<tr><td><strong>TTFB</strong></td><td>从请求发出到首字节（DevTools 的 Waiting）</td><td>服务器 / CDN 回源、排队、后端</td><td>Network 的 waiting、Server-Timing</td></tr>
<tr><td><strong>FCP</strong></td><td>首次绘制文字 / 图像</td><td>渲染阻塞 CSS、阻塞解析脚本、字体</td><td>Critical request chain</td></tr>
<tr><td><strong>LCP</strong></td><td>视口内最大内容元素完成绘制</td><td>首图发现晚、图片太大、TTFB 高、字体阻塞</td><td>LCP 元素、preload、图片格式</td></tr>
<tr><td><strong>INP</strong></td><td>交互到下一帧绘制的延迟</td><td>长任务、水合、大量同步 JS</td><td>Performance 的 long tasks</td></tr>
<tr><td><strong>CLS</strong></td><td>非预期布局位移</td><td>图片 / 广告 / 字体 / 动态插入内容没有预留空间</td><td>Layout Shift 区域与来源</td></tr>
</tbody>
</table>
</Table>

<Callout type="info">
	**INP 已取代 FID。** FID 只测「第一次输入到事件处理器开始」的延迟；INP 观察整次访问中的交互，测量从输入到下一帧真正绘制的时间。它更接近用户感受到的「卡不卡」。
</Callout>

字体是首屏最常见的隐形阻塞：`font-display: block` 在字体到达前可能让文字不可见；`swap` 先画后备字体，字体到了再替换，速度快但可能造成 CLS。`preload` 关键字体、用 `size-adjust` / `ascent-override` 匹配后备字体，比单纯调 `font-display` 更完整。

图片方面，首屏主图不要 `loading="lazy"`：lazy 会让浏览器晚发现它，LCP 直接后移。给图片写死 `width` / `height` 或用 `aspect-ratio` 预留空间；用 `srcset` / `sizes` 让浏览器按视口选尺寸；`fetchpriority="high"` 可以把 LCP 候选的优先级提上来。

<Formula>
	LCP ≈ TTFB + 资源加载延迟 + 资源加载时长 + 元素渲染延迟
</Formula>
<Caption>
	这是官方的 LCP 分解方式。先判断时间花在「服务器首字节」「发现资源太晚」「下载太慢」还是「下载完了但主线程没空画」，再决定优化哪一段。
</Caption>

<Callout type="warn">
	**`load` 事件不是终点。** async 脚本可能在 load 之后才执行；懒加载图片、字体替换、水合和用户输入都可能发生在 load 之后。用 Core Web Vitals 和真实用户监控（RUM）看 p75，而不是只看本地 Lighthouse 的一次跑分。
</Callout>

<Disclosure title="bfcache 与 pageshow：返回页面为什么不重新加载？">
	浏览器可以把整个页面冻结在内存里，前进 / 后退时直接恢复，连 JS 堆都保留。恢复时 `pageshow` 的 `event.persisted` 为 `true`；首次加载通常为 `false`。
	如果页面依赖「每次进入都重新初始化」，要在 `pageshow` 里检查并刷新状态；不要在 `unload` 里做清理，它可能阻止 bfcache。用 `pagehide` / `visibilitychange` 处理离开与恢复。
</Disclosure>

## 第十二站：把一次导航摊平在时间轴上

把前面的站点放进一条时间线，会看到「慢」通常不是某一个点，而是几段串联的等待。下表是一组示意值，假设 RTT 约 50ms、无缓存、主文档串行；真实页面会被 CDN、并发、缓存和设备改写。DevTools 的 Waiting (TTFB) 只对应「服务器等待」这一段；从导航开始到首字节，还要加上前面的 DNS、连接与 TLS。

</Callout>

<Disclosure title="一页纸的排查清单">
	1. 主文档的 `Cache-Control` / `ETag` 是否符合预期？<br />
	2. 首屏是否有阻塞解析的经典脚本？能否 `defer` 或移到模块？<br />
	3. 关键 CSS 是否被 `@import` 或第三方样式串行拖慢？<br />
	4. LCP 图是否 `eager`、有 `srcset`、必要时 `preload`？<br />
	5. 字体是否阻塞文字？是否需要 `preload` + `size-adjust`？<br />
	6. 是否存在水合长任务或大量同步第三方脚本？<br />
	7. 图片 / 广告 / 动态内容是否预留了空间，避免 CLS？<br />
	8. 是否被 bfcache 影响，返回时状态没有刷新？<br />
	9. 关键第三方域名是否 `preconnect`，而不是给所有域名预热？<br />
	10. 以上是否在真实用户的 p75 上验证，而不是只看本地一次跑分？
</Disclosure>

## 常见误解：八句话，八个更准确的说法

<Table>
<table>
<thead><tr><th>常见说法</th><th>更准确的说法</th></tr></thead>
<tbody>
<tr><td>HTML 下载完才开始渲染</td><td>解析是流式的；CSS 阻塞渲染，经典脚本阻塞解析，首帧可以在 HTML 下完之前出现。</td></tr>
<tr><td>DOMContentLoaded 就是页面加载完成</td><td>它只表示 HTML 解析完成、deferred 脚本执行完；load 还要等资源，可交互更晚。</td></tr>
<tr><td>304 是错误</td><td>304 是条件请求验证成功，复用旧正文；它不是失败状态。</td></tr>
<tr><td>no-cache 是不缓存</td><td>no-cache 是「用前必须验证」；no-store 才是不允许存储。</td></tr>
<tr><td>HTTP/2 一定比 HTTP/1.1 快</td><td>它减少连接数和头部开销，但 TCP 丢包会阻塞所有流；优先级、服务器配置和页面结构同样重要。</td></tr>
<tr><td>HTTPS 隐藏了访问域名</td><td>DNS、SNI、IP 默认仍可能可见；ECH 只解决一部分，且并非普遍可用。</td></tr>
<tr><td>CDN 只是缓存</td><td>CDN 还做 TLS 终止、压缩、边缘计算、路由与抗攻击；缓存只是其中一层。</td></tr>
<tr><td>所有图片都该 lazy</td><td>首屏 LCP 图 lazy 会推迟发现与绘制；lazy 适合首屏之外、滚动才需要的图片。</td></tr>
</tbody>
</table>
</Table>

<Callout type="tip">
	**如果只记三件事：** 第一，先分清「导航 / 网络 / 解析 / 渲染」四段，再谈优化；第二，缓存与连接复用往往比换协议更能改变首字节；第三，首屏的关键路径是 CSS、脚本和 LCP 资源，不是「所有资源」。
</Callout>
